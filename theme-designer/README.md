# Theme Designer: Constraint-Solved Color Schemes with Point-CAD

A color scheme is a small set of colors that must stand in _relations_ to
each other: text must contrast with its background, surfaces must step up in
lightness by even amounts, the accent must sit opposite the brand hue, the
"danger" red must read as red in both the light and the dark theme, and
everything must stay inside the sRGB gamut. Designers currently satisfy these
relations by hand, per theme, and break them again on the next tweak.

This document applies **Point-CAD** to that problem. Colors become labeled
points in a perceptual color space, design rules become constraints, and
light/dark/high-contrast variants become different _input sets_ solved over
one shared model. The output is CSS custom properties (or design tokens)
regenerated by the solver whenever a rule or an anchor color changes.

Point-CAD already provides points, variables, constraints, macros, a
pluggable space abstraction and a Gauss-Newton solver. The color domain fits
that shape closely but needs a handful of additions, most of them useful
well beyond colors:

- a perceptual **color space** registered as a Point-CAD `Space` (§4),
- constraints that act on a **single coordinate axis** rather than on the
  full geodesic distance — "these two colors have the same lightness" (§5.1),
- **linked measures**: one distance expressed arithmetically or
  geometrically in terms of another (§6.1),
- **inequality targets** ("contrast ≥ 4.5") in addition to equality and
  objective targets (§6.2),
- **scenarios**: solving one model over several input sets, optionally
  with variables shared between them (§6.3).

---

## 1. Goals

- **One model, many themes.** The palette's _structure_ (which color relates
  to which, and how) is written once. Each theme supplies only a few anchor
  colors; the solver derives the rest.
- **Perceptual by construction.** All solving happens in a perceptually
  uniform space (OKLab by default, CIELAB optional) so that "equal steps"
  and "equal distance" mean what a human sees, not what the RGB bytes say.
- **Accessibility as a hard constraint.** WCAG 2.x contrast ratios and APCA
  lightness contrast are first-class measures, so themes cannot be generated
  that violate a stated minimum.
- **Gamut-safe output.** Every exported color is constrained to lie inside
  the target gamut (sRGB, optionally Display-P3); no clipping after the fact.
- **Reuse Point-CAD unchanged where possible.** The theme designer is an
  `extensions/theme/` package plus a demo page. Anything it cannot express
  with the existing registry becomes a _generic_ core addition (§6), never a
  color-specific special case in the core.
- **CSS out of the box.** `emitCSS()` writes `:root` blocks with
  `oklch()`/`rgb()`/hex values and `prefers-color-scheme` / `data-theme`
  switching; `emitTokens()` writes W3C Design Tokens JSON.

## 2. Non-Goals (for v1)

- Full color-management (ICC profiles, CMYK, HDR tone mapping).
- Image-based palette extraction; inputs are typed or picked, not sampled.
- Color-vision-deficiency simulation as a _constraint_. It is a natural
  later measure (§11) but v1 ships only as a preview filter.
- Component-level theming (buttons, cards). v1 produces named color
  tokens; mapping tokens onto components is the host's job.

## 3. Mapping the Domain onto Point-CAD

| Point-CAD concept    | Theme designer meaning                                                    |
| -------------------- | ------------------------------------------------------------------------- |
| sketch document      | a **palette model**: colors + rules + themes                              |
| space                | a **color space** (`oklab`, `cielab`, …)                                  |
| point                | a **color**; coordinates are `[L, a, b]`                                  |
| seed                 | the designer's initial guess / previous solution                          |
| `fixed` point        | an **anchor** whose value a theme dictates (brand color, page background) |
| variable             | a **design scalar** (surface step size, muted-text contrast, hue spread)  |
| `distance`           | perceptual difference **ΔE** between two colors                           |
| `angle`              | angle at a color between two others (rarely useful; kept for free)        |
| constraint           | a **design rule**                                                         |
| macro                | a **recipe** ("surface ramp of 4 steps", "complementary accent pair")     |
| solve                | **generate** a theme                                                      |
| scenario (new, §6.3) | a **theme**: one assignment of anchor colors and theme-scoped variables   |

### 3.1 Colors as points

A color point is an ordinary Point-CAD point with two extra flags supplied
by the extension's entity schema:

```js
{ id: "P1", label: "canvas",   seed: [0.98, 0.00,  0.00], fixed: true,  role: "anchor",      export: true  }
{ id: "P2", label: "brand",    seed: [0.55, 0.12, -0.18], fixed: true,  role: "anchor",      export: true  }
{ id: "P3", label: "warmth",   seed: [0.70, 0.05,  0.10], fixed: true,  role: "orientation", export: false }
{ id: "P4", label: "text",     seed: [0.20, 0.00,  0.00], fixed: false, role: "derived",     export: true  }
{ id: "P5", label: "surface1", seed: [0.95, 0.00,  0.00], fixed: false, role: "derived",     export: true  }
{ id: "P6", label: "mid",      seed: [0.60, 0.00,  0.00], fixed: false, role: "helper",      export: false }
```

- **Anchors** (`role: "anchor"`) are inputs. They are `fixed` for the solver
  and are normally exported too (the brand color is both an input and a
  token). Themes override anchor positions (§3.3).
- **Orientation points** (`role: "orientation"`) are inputs that are _not_
  colors anyone will use. They exist to steer derived colors: a `warmth`
  point that surfaces are pulled toward, a `neutralAxis` point that keeps
  grays truly neutral, a `readingGray` point that text hue is locked to.
  They are `fixed`, never exported, and drawn as hollow markers in the UI.
- **Derived** colors (`role: "derived"`) are outputs: free points the solver
  positions. They are exported.
- **Helpers** (`role: "helper"`) are free but unexported — midpoints,
  parallelogram corners and other scaffolding created by macros, exactly as
  in the geometric sketcher.

`role` is a convenience; the solver only ever sees `fixed`, and the emitter
only ever sees `export`. The two flags default from the role but can be set
independently.

### 3.2 Design scalars

Variables are unchanged. Typical ones:

```
var stepL     = 0.04            # lightness step between surfaces
var mutedC    = 4.5   locked    # contrast ratio for secondary text
var hueSpread = 30    locked    # degrees between analogous accents
var accentC                     # free: solver picks a chroma
```

Variables can be **theme-scoped** (§3.3): the dark theme may override
`stepL` because equal perceptual steps in a dark UI usually want to be
smaller.

### 3.3 Themes as input sets

A **theme** is a named set of overrides applied to anchors, orientation
points and variables before solving:

```
theme light {
  canvas at oklch(98% 0.005 90)
  brand  at #3b5bdb
  warmth at oklch(70% 0.06 70)
}

theme dark {
  canvas at oklch(16% 0.01 260)
  brand  at oklch(72% 0.14 262)
  warmth at oklch(40% 0.03 260)
  var stepL = 0.03
  var polarity = -1
}
```

Points not mentioned in a theme keep their model seed. Solving the model
_over_ its themes (§8) produces one solved point set per theme; the emitter
writes each as a CSS block. Themes are the concrete form of the generic
**scenario** mechanism proposed for the core in §6.3.

## 4. Color Spaces as Point-CAD Spaces

Nothing in the Point-CAD core touches coordinates directly, so color spaces
plug in through `registry.registerSpace()`. Two are planned.

### 4.1 `oklab` (default)

```js
registry.registerSpace({
  id: "oklab",
  dim: 3,                                         // [L, a, b], L in [0,1]
  distance(p, q)   => hypot(q[0]-p[0], q[1]-p[1], q[2]-p[2]),   // ΔE_ok
  angle(p, q, r)   => euclideanAngle(p, q, r),
  interpolate(p, q, t) => lerp(p, q, t),
  normalize(c)     => c,                          // Cartesian: no gauge to fix
  toDisplay(c)     => [c[1] * 400, c[2] * 400, c[0] * 400],   // Lab cube, L up
  fromDisplay(d)   => [d[2] / 400, d[0] / 400, d[1] / 400],

  // capabilities beyond the core Space interface, discovered by name (§6.4)
  toLinearSRGB(c)  => [r, g, b],                  // may fall outside [0,1]
  fromLinearSRGB(rgb) => [L, a, b],
  toPolar(c)       => [L, C, h],                  // h in degrees
  fromPolar([L, C, h]) => [L, a, b],
  axes: ["L", "a", "b"],
  polarAxes: ["L", "C", "h"],
});
```

OKLab is Euclidean in its Cartesian form, so the built-in `distance` kind
_is_ ΔE and the Gauss-Newton solver works unchanged. Chroma and hue are
derived quantities exposed via `toPolar()`; they are **measured** on demand
but never used as **unknowns**, which sidesteps the wrap-around problem of
a cyclic hue coordinate in the solver (§4.3).

### 4.2 `cielab`

Identical interface with CIE L\*a\*b\* coordinates (`L` in `[0,100]`),
D65 white, and `distance` implemented as ΔE\*ab (plain Euclidean) or
optionally ΔE2000 via a `deltaE: "2000"` space option. ΔE2000 is not a true
metric and is expensive, so it is off by default.

### 4.3 Why Cartesian unknowns, polar measures

An `oklch` space with `[L, C, h]` coordinates is tempting since designers
think in lightness/chroma/hue, but the hue axis is a circle. As unknowns,
cyclic coordinates need `normalize()` to wrap after every step and make the
numerical Jacobian discontinuous at the seam; near `C = 0` the hue is also
undefined and the Jacobian degenerates. Keeping `[L, a, b]` as unknowns and
computing `C = hypot(a, b)`, `h = atan2(b, a)` only inside measures keeps
the problem smooth. Hue _differences_ are computed as the shortest signed
arc in `(-180°, 180°]`, which is smooth everywhere except at exactly 180°.

The script layer still accepts `oklch(...)`, `#rrggbb`, `rgb(...)` and
`hsl(...)` literals for seeds and anchors; they are converted once at parse
time (the same "seed expressions only" rule as vector arithmetic in PCS).

### 4.4 Gamut

The sRGB gamut is a curved, bounded region in OKLab. The space exposes
`toLinearSRGB()`; the extension provides a `gamut` measure (§5.3) built on
it. The viewport can draw the gamut hull as a wireframe of iso-lightness
slices so the designer sees why a saturated accent refuses to get any
lighter.

## 5. Color Constraint Kinds

All kinds below register through `registry.registerConstraintKind()` with a
`measure`, an `arity`, a PCS `syntax` hint and a `requires` list of space
capabilities (§6.4). They are ordinary constraint kinds: any target kind
(`value`, `variable`, `min`/`max`, and the new inequality targets) applies.

### 5.1 Axis measures and isometric locking

The most common design rule is about a **single axis**: same lightness,
same hue, chroma stepped by a fixed amount. That is not a geodesic distance
— two colors can have identical `L` and be far apart in ΔE — so it needs
its own measures.

| kind | arity | measure                                          | notes                   |
| ---- | ----- | ------------------------------------------------ | ----------------------- |
| `dL` | 2     | `L(B) − L(A)`                                    | signed                  |
| `dC` | 2     | `C(B) − C(A)`                                    | signed                  |
| `dH` | 2     | shortest signed hue arc from `A` to `B`, degrees | in `(−180, 180]`        |
| `L`  | 1     | `L(A)`                                           | absolute                |
| `C`  | 1     | `C(A)`                                           | absolute                |
| `H`  | 1     | `h(A)`                                           | absolute; wraps mod 360 |

**Isometric locking** — "these points share a coordinate" — is then
`dL A B = 0`, `dH A B = 0`, and so on. Because it is so common, the
extension registers a macro-like sugar that expands over any number of
points:

```
lock L canvas surface1 surface2 surface3      # → dL canvas surface1 = 0, dL canvas surface2 = 0, …
lock H brand accent link                       # hue-locked family
lock C surface1 surface2                       # equal chroma
```

`lock` is registered as a _variadic_ constraint kind (`arity: { points:
"2+" }`) whose `measure` returns a **vector** of residuals rather than a
scalar. Vector-valued measures are a small core generalization (§6.5); the
alternative is a pure macro, which works today but creates `n−1` separate
constraints in the list.

Locks against **orientation points** are how inputs steer outputs:
`lock H readingGray text textMuted` keeps all text on the hue of an
orientation point that the theme sets; `dL canvas surface1 = stepL`
with `stepL` negative in dark mode reverses a ramp.

### 5.2 Contrast

| kind       | arity | measure                                               | requires       |
| ---------- | ----- | ----------------------------------------------------- | -------------- |
| `contrast` | 2     | WCAG 2.x ratio `(Y_hi + 0.05) / (Y_lo + 0.05)`, `≥ 1` | `toLinearSRGB` |
| `apca`     | 2     | APCA `Lc` of `(text, background)`, signed             | `toLinearSRGB` |

`contrast` is symmetric; `apca` is not — order is `text background` and
the sign encodes polarity (negative for light text on dark), which is
handy: `apca text canvas <= -60` states "light text on a dark canvas with
at least Lc 60" in one line. Both measures are computed on _linear_ sRGB
after conversion from the working space and are gamut-agnostic (they
evaluate fine for out-of-gamut colors; the `gamut` constraint handles
that separately).

Typical use is with the inequality targets of §6.2:

```
contrast text canvas >= 7          # AAA body text
contrast textMuted canvas >= 4.5   # AA
contrast border canvas >= 3        # UI component minimum
contrast link canvas >= 4.5
```

Contrast measures are non-smooth at `Y_hi == Y_lo` (the `max`/`min`
swap). In practice text and background never meet there, and damped
Gauss-Newton with numerical Jacobians rides through it; the diagnostics
panel flags any constraint sitting within ε of a kink.

### 5.3 Gamut

| kind    | arity | measure                                                    | requires       |
| ------- | ----- | ---------------------------------------------------------- | -------------- |
| `gamut` | 1     | `max(0, max_i(rgb_i − 1), max_i(−rgb_i))` over linear sRGB | `toLinearSRGB` |

Zero inside the gamut, positive outside, growing linearly with the excess.
Used as `gamut accent <= 0` for every exported color; the extension adds
these automatically for `export: true` points unless the model says
`gamut off`. A `gamut … p3` variant selects Display-P3 primaries when the
space provides `toLinearP3`.

### 5.4 Reusing the built-ins

- `distance A B = x` is ΔE — "these two states should differ by a just
  noticeable amount" (`≈ 0.02` in OKLab for hover states).
- `distance brand accent -> max` with `gamut accent <= 0` and
  `lock L brand accent` finds the most distinct accent of equal lightness.
- `angle A B C` is available but rarely meaningful for colors; it is kept
  because it costs nothing.

### 5.5 Recipes as macros

```
def ramp(base, n, step) {                 # n derived surfaces in even L steps
  repeat i in 1..n {
    point base_i at base + (i * step, 0, 0)  role derived
    dL base base_i = i * step
    lock H base base_i
    lock C base base_i
  }
}

def complementary(A, B) {
  dH A B = 180
  lock L A B
  lock C A B
}

def hoverPair(rest, hover) {
  point hover at rest role derived
  lock H rest hover
  lock C rest hover
  dL rest hover = hoverStep              # theme-scoped var: +/− depending on polarity
}

ramp canvas 3 stepL
complementary brand accent
hoverPair accent accentHover
```

`repeat` and expressions in seeds/targets (`i * step`) lean on the v1.1
"variable expressions" item of the core roadmap; until then `ramp` is
unrolled by hand.

## 6. Additions Proposed for the Point-CAD Core

Each item below is generic — it is stated in terms of measures, targets
and problems, not colors — and would be useful in the geometric sketcher
too. The theme designer is simply the first client that needs all of them.

### 6.1 Linked measures (arithmetic and geometric)

Today a constraint's target is a literal, a variable, or an objective.
Designers constantly want one measure defined _relative to another_:
"surface3 is 1.5× as far from canvas as surface2", "the muted text
lightness step is the main step plus 0.02". Equal-variable tricks cover
the `x = y` case only.

Proposal: a `measure` target kind that references another constraint's
measure through an affine map.

```js
{ id: "C7", type: "dL", points: ["canvas", "surface3"],
  target: { kind: "measure", ref: "C6", scale: 1.5, offset: 0 } }        // x = 1.5·y

{ id: "C8", type: "dL", points: ["canvas", "textMuted"],
  target: { kind: "measure", ref: "C5", scale: 1,   offset: 0.02 } }     // x = y + 0.02
```

Residual: `r = measure(C7) − (scale · measure(C6) + offset)`. The
referenced constraint may itself be `disabled` (it then acts purely as a
named measure), and reference chains must be acyclic (validated at build
time). For **ratios** that should be scale-free (`x/y = k` with both free),
an optional `log: true` switches the residual to
`log(m_x) − log(m_y) − log(k)`, which treats a 2× and a 0.5× error
symmetrically; it requires positive measures.

PCS syntax reuses the equality form with a measure expression on the right:

```
dL canvas surface2 = stepL              id S2
dL canvas surface3 = 1.5 * @S2          # geometric link
dL canvas textMuted = @S1 + 0.02        # arithmetic link
distance A B = 2 * distance C D         # inline anonymous measure (creates a disabled C D constraint)
```

`@ID` names a constraint; a bare `KIND pts…` on the right is sugar that
creates a hidden, disabled constraint to reference. This is the "distance
linked to another distance" feature from the original note, generalized to
every measure kind.

### 6.2 Inequality targets

Contrast and gamut rules are one-sided. Add two target kinds:

| kind      | meaning                      | residual                   |
| --------- | ---------------------------- | -------------------------- |
| `atLeast` | `measure ≥ value / variable` | `max(0, target − measure)` |
| `atMost`  | `measure ≤ value / variable` | `max(0, measure − target)` |

Hinge residuals are zero once satisfied, so a satisfied inequality drops
out of the Jacobian and stops fighting the objectives — exactly the
behaviour wanted for "at least AA contrast, otherwise get out of the way".
An optional `margin` softens the hinge into a smooth approximation
(`softplus`) for solvers that dislike the kink. PCS: `>=` and `<=`.

Diagnostics report inequalities separately as _active_ (binding, residual
was nonzero during the final iterations) or _slack_.

### 6.3 Scenarios (multi-input solving)

A **scenario** is a named set of overrides on `fixed` points' positions and
on variable values:

```js
scenarios: [
  { id: "light", points: { canvas: [0.98, 0.00, 0.00], brand: [...] }, variables: { polarity: 1 } },
  { id: "dark",  points: { canvas: [0.16, 0.00, -0.01], brand: [...] }, variables: { polarity: -1, stepL: 0.03 } }
]
```

`buildProblem(sketch, { scenarios })` builds one **stacked problem**:

- Every non-fixed point gets an independent set of unknowns _per scenario_.
- Variables are **per-scenario by default** (each theme may settle on its
  own `accentC`) but may be declared `shared`, in which case one unknown
  serves all scenarios and the residuals of every scenario pull on it. This
  is how "the light and dark themes use the _same_ accent chroma, whatever
  it turns out to be" is stated.
- Each scenario's residuals are appended; the Jacobian is block-diagonal
  except for shared-variable columns, so cost is linear in the number of
  scenarios.

`SolveResult` gains `perScenario: { [id]: { points, variables, residuals } }`,
and `adopt` can adopt one scenario's solution as the model seeds. Solving a
sketch with no scenarios is the degenerate single-scenario case, so
existing behaviour is unchanged.

PCS: `theme` (registered by the extension) is sugar for `scenario`; the
core statement is

```
scenario dark { point canvas at (…)  var stepL = 0.03 }
var accentC shared
solve scenarios            # or: solve scenario dark
```

### 6.4 Space capabilities

Constraint kinds today declare `spaces: "*" | [ids]`. Naming space ids does
not scale once several color spaces (and later several curved spaces)
exist. Proposal: kinds declare `requires: ["toLinearSRGB"]` and the
registry checks that the active space object has those methods. `spaces:`
stays as an explicit allow/deny list for the rare cases that need it.

### 6.5 Vector-valued measures

Allow `measure()` to return `number | number[]`; the problem builder
appends one residual per component. This enables variadic kinds such as
`lock` (§5.1) and, in the geometric sketcher, a native `coplanar` over
`n` points or a `pointOnCurve` that returns two residuals. Objective
targets (`minimize`/`maximize`) on a vector measure apply to its norm.

### 6.6 Coordinate-literal hooks in the parser

The PCS grammar's `vec3` is fixed to `(x, y, z)` tuples and identifier
arithmetic. Let a space register **literal parsers** so
`oklch(70% 0.14 262)`, `#3b5bdb`, `rgb(59 91 219)` and `hsl(…)` are valid
seed expressions when the space understands them. The emitter asks the
space for a `preferredLiteral()` so files round-trip in the notation the
designer wrote.

## 7. Full Example

```
# palette.pcad — one model, two themes
space oklab
gamut srgb                               # auto-add `gamut P <= 0` for every exported point

var stepL     = 0.04                     # per-theme by default
var hoverStep = 0.06
var polarity  = 1      locked            # +1 light theme, −1 dark theme
var accentC   shared                     # same chroma in every theme, value chosen by solver

# ---- inputs -------------------------------------------------------------
point canvas      at oklch(98% 0.005 90)   anchor
point brand       at #3b5bdb               anchor
point warmth      at oklch(70% 0.06 70)    orientation      # pulls surfaces warm
point readingGray at oklch(50% 0.01 260)   orientation      # hue for all text

# ---- outputs ------------------------------------------------------------
point surface1 at canvas   derived
point surface2 at canvas   derived
point surface3 at canvas   derived
point text      at canvas  derived
point textMuted at canvas  derived
point border    at canvas  derived
point accent    at brand   derived
point accentHover at brand derived
point link      at brand   derived

# surfaces: even steps, slightly toward `warmth`
dL canvas surface1 = stepL                 id S1
dL canvas surface2 = 2 * @S1
dL canvas surface3 = 3 * @S1
lock C surface1 surface2 surface3
dH warmth surface1 = 0   weight 0.3        # soft hue pull
distance warmth surface3 -> min weight 0.1

# text: locked to reading hue, contrast-driven lightness
lock H readingGray text textMuted border
lock C readingGray text textMuted
contrast text canvas      >= 7
contrast textMuted canvas >= 4.5
contrast border canvas    >= 3
dL canvas text * polarity  <= 0            # text is darker in light theme, lighter in dark
distance canvas text -> min weight 0.05    # …but no darker than it has to be

# accents
complementary brand accent
C accent = accentC
contrast accent canvas >= 3
hoverPair accent accentHover
lock H brand link
contrast link canvas >= 4.5
distance link brand -> min

# ---- themes -------------------------------------------------------------
theme light {
  canvas at oklch(98% 0.005 90)
  brand  at #3b5bdb
}
theme dark {
  canvas      at oklch(16% 0.01 260)
  brand       at oklch(72% 0.14 262)
  warmth      at oklch(40% 0.03 260)
  readingGray at oklch(85% 0.01 260)
  var stepL     = 0.03
  var hoverStep = -0.06
  var polarity  = -1
}

solve scenarios
emit css --prefix color- --format oklch --switch media,attribute
```

`dL canvas text * polarity <= 0` uses a variable expression on the _left_;
strictly this is the v1.1 expression feature. Without it, the same rule is
`dL canvas text = textStep` with `textStep` given a sign per theme and the
contrast constraints doing the rest.

## 8. Solving Over Themes

1. Build the stacked problem (§6.3): one unknown block per theme for every
   derived/helper point, per-theme variable blocks, one block for shared
   variables.
2. Seed each theme's block from the model seeds, or — when re-solving after
   an edit — from that theme's previous solution (`solver.reseed:
"previous"`), which keeps small edits from flipping colors across the
   hue circle.
3. Run the default damped Gauss-Newton. Inequality hinges and the `max`
   inside contrast are the only non-smooth spots; the LM damping handles
   them for palettes of this size (tens of colors, ~100 constraints,
   2–4 themes → well under 100 ms).
4. Report per theme: converged, residuals, active inequalities, and any
   exported point that ended outside the gamut (should be impossible when
   `gamut` constraints are on; reported anyway).
5. **Under-constrained** palettes are the norm — a gray with only a
   contrast rule has a whole sheet of solutions. The nearest-to-seed
   least-squares answer is the right default here; the diagnostics simply
   list which points have slack and along which axis.
6. **Over-constrained** palettes are the interesting failure: "AAA text,
   locked to the brand hue, at chroma 0.1, on this canvas" may be
   unreachable in sRGB. Per-constraint residuals point at the culprit; the
   UI offers to relax the weakest weighted constraint or to turn a `value`
   target into an objective.

## 9. Output

### 9.1 CSS

`emitCSS(sketch, result, options)`:

```css
:root {
  --color-canvas: oklch(98% 0.005 90);
  --color-surface-1: oklch(94.1% 0.007 84);
  --color-text: oklch(21.3% 0.011 260);
  /* … every export:true point, kebab-cased label */
}
@media (prefers-color-scheme: dark) {
  :root {
    --color-canvas: oklch(16% 0.01 260); /* … */
  }
}
[data-theme='dark'] {
  --color-canvas: oklch(16% 0.01 260); /* … */
}
[data-theme='light'] {
  --color-canvas: oklch(98% 0.005 90); /* … */
}
```

Options: `prefix`, `format` (`oklch` | `rgb` | `hex`; hex/rgb are
gamut-clipped and rounded, with a comment noting the exact value),
`switch` (`media`, `attribute`, `class`, or a custom selector template),
`defaultTheme`, and `fallback: true` to emit `rgb()` before `oklch()` for
older browsers.

### 9.2 Design tokens

`emitTokens()` writes W3C Design Tokens JSON with `$type: "color"`, one
group per theme, plus a `$extensions.pointcad` block carrying the residual
and the constraint ids that bind each color, so downstream tools can show
_why_ a color is what it is.

### 9.3 Round-trip

The `.pcad` file is the source of truth. CSS and tokens are derived
artifacts; the emitter writes a header comment with the source file name
and a hash so drift is detectable.

## 10. UI

The theme designer embeds `<point-cad>` and adds panels through the same
panel registry the built-in panels use.

1. **Theme tabs** – one tab per scenario; the whole UI (swatches, viewport,
   residual colors) shows the selected theme's solution. A "compare" mode
   splits the swatch board.
2. **Swatch board** – exported colors as tiles, each rendered _on_ the
   color it is most often constrained against (text tiles on canvas, etc.),
   with the token name, `oklch()` value and the binding constraints'
   status dots. Anchors have a color picker; editing one is a theme
   override and triggers re-solve on release (live solving stays opt-in as
   in the core).
3. **Contrast matrix** – foreground × background grid of WCAG/APCA values
   colored by pass level; clicking a cell adds or focuses the constraint.
4. **Lab cube viewport** – the standard 3D viewport with `L` vertical, the
   sRGB gamut hull as wireframe slices, anchors as filled markers,
   orientation points hollow, derived points as swatch-colored spheres,
   and glyphs for `lock` (dashed iso-line) and `dH` (arc). Dragging a
   derived point edits its seed exactly as in the sketcher.
5. **Constraints panel** – the core panel, with the color kinds' forms:
   a contrast form with an AA/AAA preset dropdown, a `lock` form with an
   axis toggle and multi-select.
6. **Preview** – an iframe of a sample page consuming the emitted CSS,
   re-injected on every solve, with optional CVD simulation filters.
7. **Script panel** – unchanged; `theme` blocks and color literals appear
   as written.

## 11. Architecture

```
point-cad/
  core/                    # as before, plus the §6 additions:
    problem.js             #   scenarios, measure targets, hinge targets, vector measures
    registry.js            #   `requires` capabilities, literal parsers
  extensions/theme/
    space-oklab.js         # OKLab Space + sRGB/P3 conversions + literal parsing
    space-cielab.js        # CIELAB Space
    measures-color.js      # dL dC dH L C H, contrast, apca, gamut
    constraints-color.js   # registerConstraintKind for the above, `lock` variadic kind
    themes.js              # `theme` statement → scenarios; `gamut` auto-constraints
    recipes.pcad           # ramp, complementary, hoverPair, analogous… as macros
    emit-css.js
    emit-tokens.js
    ui/
      theme-tabs.js
      swatch-board.js
      contrast-matrix.js
      preview.js
      glyphs-color.js      # lock / dH / gamut hull glyphs for the viewport
    index.js               # registers everything; exports emitCSS/emitTokens
  demo/theme.html          # standalone theme designer page
```

Layering rules from the main design hold: `extensions/theme/` depends on
`core/` and `lang/` via the registry only; only `space-*.js` files touch
raw coordinates or do color conversion math; the UI pieces depend on the
public element API.

## 12. Open Questions

- **Which contrast measure is primary?** WCAG 2.x is the legal baseline;
  APCA matches perception far better and encodes polarity. Ship both, but
  which does the "AA" preset button insert?
- **Per-theme vs. shared variables by default.** Per-theme is safer (each
  theme solves independently); shared is what people usually _mean_ for
  structural scalars like `stepL`. Default to per-theme with a `shared`
  keyword, or the reverse?
- **Hue at low chroma.** `lock H` between a near-gray and anything is
  numerically meaningless (hue undefined at `C = 0`). Should `dH` fade its
  weight with `min(C_A, C_B)`, or should the validator warn?
- **Gamut as constraint vs. post-clip.** Constraining is principled but
  makes `-> max` objectives crawl along the gamut boundary, where the hinge
  is non-smooth. A soft barrier (`softplus`) or a final clip-and-report
  pass may be more practical.
- **Orientation points vs. variables.** A `warmth` point could equally be
  two variables `warmHue`, `warmChroma`. Points are draggable in the cube
  and can carry several constraints at once, which is the argument for
  them — but is a point that is "not a color" confusing in a color tool?
- **Should scenarios generalize to a grid?** Brand × mode × contrast-level
  is a natural 3-axis matrix; nesting `theme` blocks or supporting
  `scenario dark.highContrast extends dark` would cover it.
- **Reseeding across themes.** Seeding the dark solve from the light
  solution keeps families consistent but can pull dark colors into the
  wrong half of the cube. Seed from own previous solution, from model
  seeds, or from a mirrored (`L → 1 − L`) copy of another theme?
- **Does `lock` belong in the core?** Axis-wise equality is
  space-independent if spaces expose named axes; a generic `lockAxis`
  kind in the core would serve the geometric sketcher too ("same z" for a
  row of points is a common request).
